# Один репозиторий базы: конфигурация и расширения рядом

Типовая база 1С — это основная конфигурация плюс несколько расширений, и каждое из них
лежит в **отдельном хранилище**. Хранить их в одном репозитории Git удобно: одна история,
один clone, состояние базы на любой момент видно целиком.

gitsync-py поддерживает такую раскладку: **один репозиторий, по подкаталогу на источник**.

```text
D:/git/база/                 <- один .git на всю базу
├── README.md                <- ваши файлы; инструмент их не трогает
├── Конфигурация/            <- источник 1: хранилище основной конфигурации
│   ├── AUTHORS  VERSION
│   └── ...выгрузка XML
├── Расширение 1/            <- источник 2: хранилище расширения
│   ├── AUTHORS  VERSION
│   └── ...
└── Расширение 2/            <- источник 3: другое хранилище расширения
    ├── AUTHORS  VERSION
    └── ...
```

## Как запустить

Декларативно, одной командой — пример: [`examples/monorepo-base.json`](../examples/monorepo-base.json).

```bash
gitsync-py sync-all --config monorepo-base.json
```

Ключи манифеста, относящиеся к общему репозиторию:

| Ключ | Уровень | Значение |
|---|---|---|
| `repository` | верхний | путь к общему репозиторию. Если его ещё нет — будет создан (`git init -b main`) |
| `subtree` | хранилище | подкаталог источника внутри `repository`; относительный путь, разделитель `/` |
| `init` | хранилище | выполнить `init` перед `sync`: создать `VERSION` и, если нужно, `AUTHORS` |

`subtree` и `workdir` взаимоисключающи: либо общий репозиторий с подкаталогами, либо
независимые рабочие копии по абсолютным путям (прежний формат из `examples/storages.json`
продолжает работать без изменений).

То же самое поштучно, без манифеста — подкаталог просто передаётся в `--workdir`:

```bash
gitsync-py init --workdir D:/git/база/Конфигурация --storage-path tcp://srv/база --storage-user gitsync
gitsync-py sync --workdir D:/git/база/Конфигурация --storage-path tcp://srv/база \
    --storage-user gitsync --jobs 2 --temp-root D:/gitsync-tmp
gitsync-py sync --workdir "D:/git/база/Расширение 1" --storage-path tcp://srv/база-расш-1 \
    --extension РасширениеПечатныхФорм --storage-user gitsync --jobs 2 --temp-root D:/gitsync-tmp
```

## Что гарантируется

* **Один `.git`.** Подкаталог источника может ещё не существовать — вложенный репозиторий
  в нём не создаётся, используется настоящий корень.
* **Коммит ограничен своим подкаталогом.** Дерево коммита берётся от `HEAD`, изменяются
  только пути источника: соседние источники, корневой `README`, чужие staged-изменения не
  попадают в коммит и не теряются. Удаление объекта в хранилище удаляет файл только внутри
  своего подкаталога.
* **Свой `VERSION` и свой `AUTHORS` у каждого источника.** Номер версии и сопоставление
  авторов независимы; автор, дата и комментарий коммита берутся из версии хранилища.
* **Общая блокировка.** Файл блокировки один на репозиторий (`.git/gitsync-py.lock`):
  параллельные запуски по разным источникам одного репозитория выстраиваются в очередь
  (`--lock-timeout`) либо завершаются понятной ошибкой, но не пишут одновременно.
* **Свой журнал транзакции у каждого источника** внутри общего `.git`. Обрыв на одном
  источнике не мешает остальным; восстановление касается только своего подкаталога, и
  перестановка порядка запусков ничего не «чинит» в чужом источнике.
* **Кириллица в именах каталогов.** Состояние рабочей копии читается без экранирования
  путей, поэтому `core.quotepath` (включён в git по умолчанию) ни на что не влияет.
  Конфигурация чужого репозитория при этом не меняется.
* **Перекрытие источников отвергается.** Вложенные подкаталоги (`Конфигурация` и
  `Конфигурация/Расширение`) отклоняются и в манифесте, и в `sync`: иначе выгрузка внешнего
  источника молча удалила бы файлы вложенного.

## Границы

* **Источники синхронизируются последовательно.** Параллельность — внутри источника
  (`--jobs`: версии выгружаются одновременно, коммиты строго по порядку номеров).
  Одновременная работа двух источников по одному репозиторию невозможна: индекс Git один.
* **Проверка «грязной копии» у источника-подкаталога ограничена его подкаталогом.**
  Незафиксированные правки в соседних подкаталогах и в корне не блокируют запуск (мы их не
  трогаем), правки внутри своего подкаталога — блокируют, как и раньше. Для раскладки
  «весь репозиторий — одна рабочая копия» проверка осталась прежней, по всему репозиторию.
* **Смешивать раскладки не следует.** Если корень репозитория сам является источником
  (`VERSION` в корне), подкаталоги-источники внутри него не защищены: корневая выгрузка
  удалит их содержимое. Это осознанно оставлено ради совместимости с upstream-раскладкой
  `workdir` / `workdir/src`.
* **Чужой `index.lock`** (работает другой процесс Git или незавершённая транзакция другого
  источника) останавливает запуск с объяснением; gitsync-py чужую блокировку не снимает.
* **Один пользователь ОС и один хост.** Блокировки — файловые, на локальной ФС; координация
  между учётными записями и хостами не проверялась (см. `docs/native-session-concurrency.md`).
* **Ветки, submodules, sparse-checkout, worktrees** в этой раскладке не проверялись.
