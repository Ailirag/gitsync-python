## Что проверяется тестами на настоящем git

* коммиты строго по возрастанию версии при экспорте, завершающемся вразнобой
  (`test_sync_commits_in_version_order_despite_out_of_order_export`);
* автор/почта/дата/комментарий и файл `VERSION` (`test_sync_preserves_author_date_and_version_marker`);
* переопределение подписи через `AUTHORS`;
* ограниченность конвейера (`--jobs`, `--queue-limit`) и изоляция каталогов на версию;
* сбой версии N не коммитит N+1, `VERSION` остаётся на последней успешной;
* повторы при временных сбоях и продолжение после обрыва без дублей коммитов;
* удаление объектов между версиями отражается в git (`git ls-files`, `git show --stat`);
* служебные файлы (`.git`, `.gitignore`, `.gitattributes`, `AUTHORS`, `VERSION`) переживают очистку;
* отмена укладывается в ограниченное время (тест требует < 6 с при 40 версиях по 0.25 с);
* грязная рабочая копия не трогается и вызывает отказ;
* пути с пробелами и кириллицей — во всех тестах рабочая копия называется «рабочая копия»;
* выход выгрузки за каталог и символьные ссылки отвергаются;
* блокировка цели: второй держатель получает `LockBusyError`, потоки сериализуются;
* argv конфигуратора: порядок `-v` после `ConfigurationRepositoryUpdateCfg`, отсутствие shell,
  маскирование паролей, таймаут.

## Слайс 13: закрытие находок приёмки Docker

Тот же стенд. Проверялось ровно то, что было названо неготовым.

### Происхождение образа сверяется, а не предполагается

Контекст сборки берётся из `git archive` **коммита**, а не из рабочего дерева:
в рабочем дереве на Windows часть файлов лежит с CRLF, и сборка «из папки» даёт
образ, который с коммитом побайтово не совпадает. Манифест (sha256 каждого blob'а)
считается **вне** продукта, чтобы репозиторий не содержал хешей самого себя.

| Сверка | Результат |
|---|---|
| Контекст сборки против blob'ов коммита | 78 файлов из 78 совпали побайтово |
| Установленный пакет в образе против blob'ов `src/gitsync/**` | 19 из 19 совпали побайтово (без «различие только в переводах строк») |
| `tempExtension.cfe` в образе | 3720 байт, sha256 `3d481624…7102` — как в дереве |

Переводы строк намеренно **не** нормализуются в продукте: `.gitattributes` уже
задаёт `eol=lf`, а рабочая копия Windows остаётся такой, какой её делает `git`.

## Непроверенные швы (честно)

1. **Нативный бэкенд не исполняется этим набором тестов.** `NativeStorageBackend` и
   `DesignerRunner` покрыты здесь только тестами на состав argv: платформы 1С на машине
   разработки нет. Сами нативные прогоны выполнялись отдельно, на выделенном стенде
   (1С:Предприятие 8.3.27.2130, синтетические хранилища): выгрузка версий основной конфигурации
   и расширений, а также раскладка «один репозиторий базы» из слайса 10. Доказательства хранятся
   вне репозитория и в него намеренно не копируются.
2. **Формат отчёта `/ConfigurationRepositoryReport` не сверялся с живым отчётом.** Парсер написан
   по структуре русскоязычного отчёта; исходники `v8storage`, которыми пользуется upstream,
   недоступны. Фикстуры синтетические.
3. **Создание временной ИБ** (`CREATEINFOBASE File=...`) не проверялось; для реальных прогонов
   предусмотрен параметр `ib_factory`, чтобы подставить готовые базы.
4. **Ожидание лицензии 1С** (повтор при «Не обнаружено свободной лицензии!») не перенесено —
   есть только общий механизм повторов.
5. **Многопроцессная блокировка** проверена в пределах одного процесса (потоки) и логикой
   атомарного создания файла; кросс-процессный тест не писался.
6. **Симлинки на Windows**: тест допускает обе ветки, так как создание симлинка требует прав;
   на Linux ветка с реальным симлинком выполняется.
7. **CI не запускался** — workflow `.github/workflows/ci.yml` добавлен, но GitHub-репозиторий
   ещё не создан (нет авторизации), прогонов не было. Это относится и к добавленной задаче
   сборки образа: сами команды выполнялись вручную на стенде (см. слайс 12), но именно как
   задача GitHub Actions они не запускались ни разу.
8. **Работа с настоящим хранилищем 1С из Linux не проверялась — упирается в лицензию.**
   Приватный образ теперь собран из настоящего комплекта 8.3.27.2130: состав компонентов,
   ключи установщика и перечень системных библиотек сняты с самого дистрибутива (`--help`
   установщика и `ldd` на установленном `1cv8`), необходимость Xvfb подтверждена запуском.
   Но лицензии у стенда нет: на первом обращении к хранилищу платформа отвечает «Не найдена
   лицензия…» (код 1), поэтому отчёт по версиям, `DumpCfg`/`LoadCfg`/`DumpConfigToFiles` и
   сверка с XML-oracle на Linux **не выполнялись**. Что закрыто, а что нет, — в
   `docs/docker-guide.md`, раздел 11.
10. **`xvfb-run` не пропускал SIGTERM — исправлено.** Остановка контейнера доставалась
   посреднику, а не синхронизации: контейнер завершался с кодом 143, обработчик в команде не
   срабатывал, то есть `stop_grace_period` в `docker/compose.yaml` не работал вовсе. Заменено
   собственной обёрткой `docker/xvfb-entrypoint.sh` (свой Xvfb + `exec`), поведение закреплено
   тестами `tests/test_native_xvfb_entrypoint.py`.
9. **Разделение доступа к хранилищу между контейнерами проверено на подменённом конфигураторе.**
   Подменён последний шов перед запуском процесса (`DesignerRunner.run`); ключ блокировки, общий
   том и порядок захвата — настоящий код. На живой платформе тот же опыт не повторялся.
