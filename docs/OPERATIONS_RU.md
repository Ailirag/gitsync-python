# Эксплуатация gitsync-py: Linux, WSL2 и Docker

## Получение исходников

```bash
git clone https://github.com/Ailirag/gitsync-python.git
cd gitsync-python
git switch --track origin/feat/container-native-gitsync
git rev-parse HEAD
```

Ветка поставки: `feat/container-native-gitsync`; она не подразумевает merge в `main`.
Для закрытого репозитория предварительно настройте авторизацию GitHub. Для повторной
установки используйте проверенный commit SHA, а не полагайтесь на неизменность ветки.
Не путайте этот репозиторий **инструмента** с `/srv/gitsync/repo`, куда выгружается 1С.

Это руководство описывает эксплуатационный контракт **stage19r1**, сверенный с
`src/gitsync/cli.py`, `sync.py`, `designer.py`, `backends.py`, `safepath.py`,
`repository_session.py`, `docker/`, `examples/` и `pyproject.toml`.
Это не инструкция по установке сервера хранилища или системы лицензирования 1С.

Все пути, имена образов и источников ниже — условные примеры. Подставляйте свои
значения в **приватных файлах вне Git**. Команды Linux выполняются в Bash из корня
исходников проекта, если явно не указан другой каталог.

## 1. Назначение и границы доказательств

Инструмент читает версии хранилища конфигурации/расширения через конфигуратор,
выгружает их в изолированных рабочих каталогах и последовательно фиксирует в Git.
Это не резервная копия информационной базы, не развёртывание конфигурации и не
проверка её бизнес-поведения. Git push выполняется отдельно.

Важные ограничения текущей поставки:

- В переданной приёмке stage19r1 на неизменяемом тестовом образе получено
  **419 passed, 19 skipped**. Это результат конкретного образа и окружения, а не
  обещание такого же количества тестов или отсутствия ошибок в любой установке.
  Пропущенный тест не равен пройденному; fixture не заменяет настоящую 1С.
- Реальные успешные запуски с `jobs=2` были. Нельзя утверждать, что лицензия
  обязательно одноместная или что параллельная выгрузка в принципе не работает.
- Наблюдались перемежающиеся отказы выдачи лицензии. **Их первопричина не доказана**.
  Наблюдение различий overlay/tmpfs не доказывает причинность файловой системы,
  неисправность сервера лицензий или число доступных лицензий.
- stage19r1 добавляет ограниченный повтор распознанного лицензионного отказа
  при выгрузке версии. Повтор не исправляет систему лицензирования и не заменяет
  отдельную проверку доступности платформы.
- Безопасный **эксплуатационный старт — `jobs=1`, один внешний слот**. Это рекомендация,
  а не значение по умолчанию парсера: в CLI и `sync-all` без явной настройки
  `jobs=4`, `queue_limit=4`, `retries=1`. Поэтому задавайте параметры явно.
- Старые документы, комментарии примеров и таблицы README могут описывать ранние
  этапы. Для ограничений stage19r1 используйте этот раздел и фактический код;
  число тестов из старых документов не переносите в новый акт приёмки.

Лицензирование у эксплуатирующей организации уже должно быть законно организовано.
Используются только правомерно полученные дистрибутивы и разрешённые способы доступа
к действующей лицензии. Здесь нет эмуляторов, генерации ключей, подмены компонентов
или обходов проверок. Увеличение параллелизма не расширяет лицензионные права.

## 2. Подготовка Linux / Windows с WSL2

### Linux

1. Выделите доверенный узел и служебного пользователя без root для рабочих запусков.
2. Установите Git, Bash и util-linux (`flock`, `stat`), Docker Engine, Compose plugin
   и Buildx по инструкции Docker для своей ОС. Не устанавливайте пакеты командой
   из случайного `curl | sh`. Доступ к Docker socket практически даёт административные
   права: не предоставляйте его недоверенным пользователям или контейнерам.
3. Проверьте Docker daemon, а не только наличие клиентского бинарника:

   ```bash
   git --version
   bash --version
   flock --version
   docker version
   docker info
   docker compose version
   docker buildx version
   ```

4. Обеспечьте доступ к реестру базового образа и пакетным репозиториям для сборки;
   для выполнения — только к нужному хранилищу, штатной системе лицензирования и,
   отдельно для отправки, Git-серверу. Правила сети согласуйте с администраторами.
5. Проверьте RAM, место на диске, синхронизацию часов и часовой пояс источника.
   Время отчёта хранилища не содержит смещения; неверный `TZ` меняет время и SHA коммитов.

Официальные инструкции: [Docker Engine](https://docs.docker.com/engine/install/),
[Compose](https://docs.docker.com/compose/install/),
[Buildx](https://docs.docker.com/build/buildx/).

### Windows / WSL2

Установите WSL2 с Linux-дистрибутивом и Docker Desktop с Linux containers и интеграцией
с этим дистрибутивом либо согласованный организацией Docker Engine внутри Linux.
Не смешивайте два daemon без явного выбора контекста. Сверьте `docker context show`
и `docker info` **из той же WSL-сессии**, где будет работать планировщик.
См. [WSL](https://learn.microsoft.com/windows/wsl/install) и
[Docker Desktop WSL](https://docs.docker.com/desktop/features/wsl/).

Сборки, launcher и права `chmod`/`flock` выполняйте внутри Linux/WSL, а не в PowerShell
или Git Bash. Рабочую копию, конфиги и очередь лучше размещать в файловой системе
Linux, а не `/mnt/c`: права, блокировки и производительность должны быть проверены
отдельно для Windows-mounted дисков. Пути контейнера всегда Linux-пути, а не `C:\...`.
WSL/Docker Desktop должен оставаться запущенным во время заданий; сон компьютера —
прерывание работы, а не штатное расписание. Отдельной полной приёмки всех режимов
WSL этим документом не заявляется.

### Вариант без контейнера

`pyproject.toml` требует Python >= 3.11; обязательных Python-зависимостей времени
выполнения нет, но нужен внешний Git. Из корня исходников:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install .
gitsync-py --help
python -m gitsync sync --help
```

Для разработки устанавливают `python -m pip install -e '.[dev]'`. Это не добавляет
платформу 1С. Для native нужны совместимые библиотеки, толстый клиент с конфигуратором,
графическое окружение и штатная лицензия. Для Linux рекомендуем приватный Docker-образ:
его Dockerfile фиксирует зависимости проверенного комплекта. `--v8-version` не ищет
и не устанавливает платформу; необходим реальный `--v8-path`.

## 3. Сборка образов core, test и native

### Core и test

```bash
docker build -f docker/Dockerfile.core --target core -t gitsync-py:core .
docker build -f docker/Dockerfile.core --target test -t gitsync-py:test .
docker image inspect --format '{{.Id}}' gitsync-py:core
docker image inspect --format '{{.Id}}' gitsync-py:test
docker run --rm gitsync-py:core --help
docker run --rm gitsync-py:test
```

`core` содержит Python, Git, SSH-клиент и установленное колесо проекта, но **не 1С**.
`test` дополнительно содержит pytest, Ruff, тесты и документы; команда по умолчанию —
`python -m pytest -q`. Результат сохраняйте вместе с кодом возврата и ID образа.
Для повторного прогона точного образа:

```bash
TEST_IMAGE=$(docker image inspect --format '{{.Id}}' gitsync-py:test)
docker run --rm "$TEST_IMAGE" python -m pytest -q
docker run --rm "$TEST_IMAGE" python -m ruff check /src/src /src/tests
```

Это отдельные проверки; результат линтера нельзя выводить из результата pytest.
Образ базируется на Debian 12 / Python 3.11 с digest в Dockerfile. Однако pip/apt
и dev-зависимости не полностью зафиксированы: **пересборка не гарантирует идентичность**.
Для приёмки важен сохранённый image ID/digest, исходный snapshot и журнал сборки,
а не только изменяемый тег `:test` или номер пакета `0.1.0`.

### Приватный native

Рецепт адаптирован под Linux x86_64 комплект **8.3.27.2130** с установщиком
`setup-full-8.3.27.2130-x86_64.run`. Это не универсальный установщик всех версий 1С.
На другой версии/архитектуре повторно проверяют имена компонентов, зависимости и
поведение платформы. Не заменяйте Debian 12 на новую базу без проверки: рецепт
использует WebKitGTK 4.0 и GTK3.

В отдельном приватном каталоге разместите только законный комплект одной версии.
Не копируйте его в Git или основной build context. Пример:

```bash
chmod u+x /srv/private/onec/setup-full-8.3.27.2130-x86_64.run
docker buildx build -f docker/Dockerfile.native \
  --build-context onec=/srv/private/onec \
  --build-arg CORE_IMAGE=gitsync-py:core \
  --build-arg ONEC_VERSION=8.3.27.2130 \
  --build-arg ONEC_SETUP=setup-full-8.3.27.2130-x86_64.run \
  --build-arg ONEC_LANGS=ru \
  -t gitsync-py:native-8.3.27.2130 --load .
docker image inspect --format '{{.Id}}' gitsync-py:native-8.3.27.2130
docker run --rm gitsync-py:native-8.3.27.2130 --help
```

BuildKit монтирует именованный контекст `onec` только на шаг установки; сам установщик
не копируется в слои. **Установленные проприетарные файлы в native-образе есть**:
образ и build cache должны оставаться приватными, не публикуйте их вместе с исходниками.
Если выбранный Buildx builder не видит локальный `gitsync-py:core`, настройте builder,
имеющий доступ к образу, или используйте разрешённый приватный registry с закреплённым
core digest. Не обходите проблему публикацией native-образа в открытый registry.

Dockerfile ставит `client_full`, проверяет наличие бинарника и отсутствующих библиотек
через `ldd`, добавляет Xvfb и шрифты. Штатная цепочка entrypoint обеспечивает запись
о UID, Xvfb, preflight и CLI. Не заменяйте её на прямой `1cv8` при обычном запуске.
Справка `gitsync-py --help` **не получает лицензию и не доказывает native-доступ**.

## 4. Данные, права и секреты

Рекомендуемая раскладка на Linux-хосте (не внутри исходников проекта):

| Путь хоста | Содержимое / режим |
|---|---|
| `/srv/gitsync/repo` | постоянная рабочая копия, включая `.git`, `AUTHORS`, `VERSION` |
| `/srv/gitsync/config` | приватные JSON-манифесты и параметры запуска, mount read-only |
| `/srv/gitsync/secrets` | пароль хранилища, отдельно учётные материалы Git; только нужному процессу |
| `/srv/gitsync/logs` | журналы запусков и приёмки с ограниченным доступом |
| общий volume `gitsync-sessions` | блокировки входа в хранилище для всех сотрудничающих контейнеров |
| `$HOME/.local/state/gitsync-admission` | файлы внешнего допуска, один хозяин и один путь для всех заданий |
| `/var/lib/gitsync/scratch` **в контейнере** | частная tmpfs; не постоянные данные и не общий volume |

Пути `/srv/...` заранее создаёт администратор и передаёт служебному UID. Не делайте
`chmod -R 777`. Для секретов — каталог 0700, файлы 0400/0600 с владельцем, который
читает их в контейнере. JSON не должен содержать пароль: только `storage_password_file`
или имя `storage_password_env`. Не добавляйте в Git даже «временно» приватные конфиги,
дампы, сырые логи, дистрибутивы и файлы настройки лицензирования. `.gitignore` не
удаляет уже опубликованный секрет; при утечке нужны отзыв/смена и отдельная процедура
очистки истории.

CLI отвергает `--storage-password`. При одновременной настройке env и file код выбирает
env; **задавайте только один способ**. Файл читается как UTF-8 с `.strip()`:
начальные/конечные пробельные символы не сохраняются. Пустая/не заданная выбранная env
вызывает ошибку. Переменные окружения не являются секретным хранилищем и доступны
администраторам/диагностике контейнера; предпочтительнее read-only файл.

Маскирование сообщений gitsync — защита от случайного вывода, не полная изоляция:
платформа получает необходимые параметры запуска, а сырые `/Out` и диагностические
артефакты могут содержать чувствительную информацию. Не включайте `set -x` и не
публикуйте `docker inspect`, JSON или DEBUG-логи без проверки/редактирования.

Лицензионные настройки подключаются **только способом, уже согласованным с
администратором 1С**, например read-only файл конфигурации в нужный каталог платформы.
Не включайте их в build args или образ. Этот документ не меняет лицензионную схему.

## 5. JSON-манифест для постоянного запуска

Пример `/srv/gitsync/config/storages.json` для одного репозитория с двумя источниками.
`SOURCE_LOGIN` и `ExtensionName` — заменяемые обозначения, не готовые учётные данные.
`storage_path` указывает на предоставленные оператором копии/источники внутри контейнера.

```json
{
  "repository": "/repo",
  "defaults": {
    "backend": "native",
    "v8_path": "/opt/1cv8/x86_64/8.3.27.2130/1cv8",
    "v8_version": "8.3.27.2130",
    "storage_user": "SOURCE_LOGIN",
    "storage_password_file": "/run/secrets/storage_password",
    "jobs": 1,
    "queue_limit": 1,
    "retries": 2,
    "designer_timeout": 3600,
    "lock_timeout": 1800,
    "temp_root": "/var/lib/gitsync/scratch",
    "disable_auto_src": true,
    "init": true
  },
  "storages": [
    {
      "name": "configuration",
      "subtree": "configuration",
      "storage_path": "/storage/configuration"
    },
    {
      "name": "extension",
      "subtree": "extensions/example",
      "storage_path": "/storage/extension",
      "extension": "ExtensionName"
    }
  ]
}
```

Удалите второй источник, если расширения нет. Для разных паролей укажите отдельные
файлы в записях. Для независимых Git-репозиториев уберите `repository` и задайте каждой
записи свой `workdir`. Нельзя смешивать `workdir` с `subtree` в одной записи, допускать
перекрывающиеся каталоги или различать их только регистром.

`sync-all` понимает верхние ключи `repository`, `defaults`, `storages`; формат upstream
с `repositories` не поддерживается. Пути JSON — пути **процесса внутри контейнера**;
автоматической shell-подстановки `${VARIABLE}` в JSON нет. Используйте абсолютные пути.
Манифест читается как UTF-8/UTF-8 BOM. Поле `disabled: true` (или `disable`) отключает
источник. Все отключённые источники могут дать exit 0 с сообщением, что ничего не
выполнено: мониторинг должен учитывать не только exit code.

Источники `sync-all` обрабатываются последовательно; `jobs` — параллельные **версии
внутри источника**, а не число хранилищ. `init: true` вызывает подготовку перед sync,
не является отдельной командой импорта. `--name` можно повторять для выбора источников.
На `sync-all` нет флага `--jobs`: изменяйте JSON, а не дописывайте неподдерживаемый ключ CLI.
Переменная образа `GITSYNC_V8_PATH` сама по себе не заменяет `v8_path` манифеста/CLI.

## 6. Штатный launcher и очередь внешних задач

Для stage19r1 предпочтителен `examples/gitsync-run.sh`: Bash + Docker + flock.
Он допускает задания одного пользователя на одном хосте через общие slot-locks,
затем создаёт частную tmpfs и запускает контейнер. Это **не durable очередь сообщений**:
нет базы задач, ack/replay, FIFO-гарантии, автоматического восстановления после reboot
или межхостового ограничения. Учет расписания и повторную подачу ведёт внешний планировщик.

Пример окружения ниже задаётся в Linux-shell; постоянную копию храните вне Git,
защитите правами и загружайте только как доверенный shell-файл. launcher **не читает
`.env` автоматически**. Файл `examples/gitsync-run.env.example` — перечень настроек,
его реальные mount/network значения нельзя бездумно копировать.

```bash
export GITSYNC_IMAGE=$(docker image inspect --format '{{.Id}}' gitsync-py:native-8.3.27.2130)
export GITSYNC_ADMISSION_DIR="$HOME/.local/state/gitsync-admission"
export GITSYNC_ADMISSION_WAIT=1800
export GITSYNC_SLOTS=1
export GITSYNC_SCRATCH=/var/lib/gitsync/scratch
export GITSYNC_SCRATCH_TMPFS=2g
export SOURCE_TZ=Etc/UTC
# Etc/UTC верно только если время ИСТОЧНИКА действительно UTC. Иначе замените.
export GITSYNC_DOCKER_ARGS="--user $(id -u):0 -e TZ=$SOURCE_TZ -e HOME=/home/app -v /srv/gitsync/repo:/repo -v /srv/gitsync/config:/config:ro -v /srv/gitsync/secrets/storage_password:/run/secrets/storage_password:ro -v /srv/gitsync/storage-copy:/storage:ro -v gitsync-sessions:/var/lib/gitsync/sessions"
docker volume create gitsync-sessions
bash examples/gitsync-run.sh --help
bash examples/gitsync-run.sh sync-all --config /config/storages.json --name configuration
```

До последней команды дополните `GITSYNC_DOCKER_ARGS` разрешёнными сетевыми параметрами
и read-only монтированиями **существующей** лицензионной конфигурации, если они нужны
вашей установке. В приведённом шаблоне никакая система лицензирования не разворачивается.
Работайте не от root, все сотрудничающие контейнеры — под одним UID. `:0` обеспечивает
групповой доступ к служебным каталогам образа; это не UID root.

В launcher `GITSYNC_DOCKER_ARGS` разбивается на слова, без `eval`: встроенные кавычки
не обеспечивают поддержку пробелов в путях. Выбирайте пути без пробелов и shell-масок;
секреты не передавайте текстом аргументов. Не добавляйте произвольные docker-флаги из
недоверенного источника.

Три разных уровня координации:

1. **Внешние слоты** `GITSYNC_SLOTS=1`: целиком сериализуют контейнерные задания,
   запущенные через один launcher/каталог очереди. Одновременная подача возможна,
   одновременное исполнение при одном слоте — нет. Запуски мимо launcher не учитываются.
2. **Блокировка Git-цели** `.git/gitsync-py.lock`: сериализует изменения одного
   репозитория, в том числе его разных subtrees. Ожидание задаёт `--lock-timeout`.
3. **Сессия хранилища** в `GITSYNC_SESSION_DIR`: ключ из пути/URI хранилища и логина;
   защищает Report/DumpCfg. Приватная обработка ИБ/LoadCfg/XML может идти параллельно.
   Ожидание в backend связано с `designer_timeout`. Одинаковое хранилище должно иметь
   одинаковый путь монтирования/URI во всех контейнерах. Разные DNS-алиасы не сводятся
   автоматически; другой хост, UID или ручной конфигуратор этой блокировкой не охвачены.

Не удаляйте slot-файлы и файлы session-lock для «разблокировки»: живой flock связан
с открытым файлом, удаление разрушает координацию. После выхода процесса OS освобождает
блокировку; наличие файла не доказывает занятость. Каталог очереди принадлежит UID
запуска и не допускает записи группой/остальными (рекомендуется 0700).

## 7. Первый init, sync и переход jobs=1 → jobs=2

Сначала используйте копию хранилища и отдельный пустой Git-каталог, без push.
Файловое подключение сначала проверьте read-only. Если платформа требует записи
служебных файлов, разрешение RW согласуйте **только для копии**, а не для production.
Сетевой путь `tcp://...` и его доступность требуют отдельной приёмки.

Для одного источника можно обойтись CLI (переменные ниже содержат только путь и логин):

```bash
V8=/opt/1cv8/x86_64/8.3.27.2130/1cv8
STORAGE=/storage/configuration
STORAGE_USER=SOURCE_LOGIN
common=(--workdir /repo --backend native --v8-path "$V8"
        --v8-version 8.3.27.2130 --storage-path "$STORAGE"
        --storage-user "$STORAGE_USER" --storage-password-file /run/secrets/storage_password
        --temp-root /var/lib/gitsync/scratch --disable-auto-src
        --jobs 1 --queue-limit 1 --retries 2 --designer-timeout 3600 --lock-timeout 1800)
bash examples/gitsync-run.sh init "${common[@]}"
bash examples/gitsync-run.sh sync "${common[@]}" --limit 1
bash examples/gitsync-run.sh sync "${common[@]}"
```

Это альтернативная **корневая раскладка**; не выполняйте её поверх monorepo из раздела 5.
`init` создаёт Git, `AUTHORS`, `VERSION` (начальный маркер 0); генерация AUTHORS требует
доступа к отчёту хранилища. `--no-authors` пропускает генерацию, но не делает native
фикстурой. Проверьте сопоставление авторов до полного импорта. `--disable-auto-src`
исключает автоматический выбор существующего `src`.

В существующий Git можно выполнить `clone --url <URL> ...`: по фактическому коду это
**git clone + init, не полная синхронизация**. После него всё равно нужен `sync`.
`--limit 1` ограничивает число новых версий, не задаёт конкретный номер версии.

Проверка результата на хосте:

```bash
git -C /srv/gitsync/repo status --short
git -C /srv/gitsync/repo log -5 --format=fuller
git -C /srv/gitsync/repo show HEAD:VERSION
```

Для monorepo последняя команда имеет путь, например `HEAD:configuration/VERSION`.
Сопоставьте AUTHORS, маркер VERSION, дерево XML и отчёт хранилища. Затем повторите
тот же sync: при отсутствии новых версий новых коммитов быть не должно. Сообщение
«Новых версий нет» после успешного отчёта — нормальный исход, но не заменяет проверку
того, что выбран правильный источник.

Только после этого на новой тестовой копии проверьте `--jobs 2 --queue-limit 2`
(для `sync-all` — `jobs: 2`, `queue_limit: 2` в JSON). Сравните последовательность
версий/авторов/дат/содержимое, отсутствие пропусков и повторных коммитов, повторите
прогоны. Сохраните внешние слоты равными 1: `jobs=2` не требует двух внешних заданий.
Не повышайте `GITSYNC_SLOTS` без отдельной проверки законной лицензионной ёмкости,
сети, памяти, нескольких репозиториев и влияния внешних клиентов.

### Повторы в stage19r1

`--retries N` означает до N дополнительных попыток экспорта версии. При `N=0`
повторов нет. Распознанный по `/Out` отказ выдачи лицензии (`LicenseUnavailableError`)
получает паузу **20 секунд** перед следующей попыткой; ожидание проверяет отмену
с шагом 0,5 секунды. Это константы кода, отдельного CLI-флага для паузы нет.

Нельзя считать любой сбой временным. Обычный `DesignerError`, таймаут, небезопасный
путь и отмена не повторяются этой веткой. **Повтор отчёта истории и init не покрыт
циклом экспорта версии**: если лицензия не выдана ещё на Report, весь запуск может
завершиться ошибкой сразу. Внешний планировщик может повторить целое задание с
ограничением числа попыток/задержкой, но должен различать временный отказ и ошибку
конфигурации; бесконечные повторы скрывают проблему.

После ошибки на версии N более поздние версии не коммитятся; уже подтверждённые
версии сохраняются, повторный запуск продолжает с последнего подтверждённого состояния.
`queue_limit` — глубина предварительной подачи сверх `jobs`, а не внешняя очередь
и не число попыток. Слишком большое значение увеличивает временные данные и RAM.

## 8. Частная tmpfs и границы безопасности

launcher сам добавляет `--tmpfs` для scratch; размер по умолчанию 2g, режим 1777.
**Не добавляйте scratch в `GITSYNC_DOCKER_ARGS`** ни через `-v`, `--mount`, ни через
собственный `--tmpfs`: launcher отвергает пересечения с scratch, его предками и
потомками кодом 78 до старта контейнера. Путь `--temp-root` также учитывается.
Подключайте рабочую копию отдельным листом `/repo`, sessions отдельным листом;
не накрывайте общим volume `/var/lib/gitsync`.

Почему это важно: обычный bind/named/anonymous volume с данными выгрузки может быть
подключён соседнему контейнеру того же UID, который прочитает или удалит данные.
Частная tmpfs и собственный слой контейнера не дают такого обычного общего пути.
`GITSYNC_REQUIRE_PRIVATE_SCRATCH=1` включает дополнительную fail-closed проверку в
Python. **Не отключайте её ради устранения ошибки конфигурации.**

Граница доверия не включает противника под тем же UID внутри своего контейнера,
администратора хоста или обладателя Docker socket. Sticky bit не защищает от того же
UID. Плагины — доверенный исполняемый Python-код, не песочница.

Размер tmpfs — потолок, а не гарантия свободной памяти; учитывайте одновременно ИБ,
CF/CFE, XML, число workers и память самой платформы. При исчерпании места/памяти
возможны ENOSPC/OOM. tmpfs может использовать swap: для чувствительных данных отдельно
настройте политику swap/шифрования хоста. `GITSYNC_SCRATCH_TMPFS=off` оставляет scratch
на слое контейнера; это диагностический/отдельно проверяемый режим, не рекомендуемый
способ получить jobs>1. Он не доказывает и не устраняет причину лицензионных отказов.

tmpfs исчезает при остановке контейнера, а launcher использует `--rm`. Поэтому
`--keep-temp` **не сохраняет артефакты после завершения такого контейнера**. Для
диагностики нужна отдельная согласованная процедура: частный контейнер без `--rm`,
сбор нужных файлов пока он жив, либо защищённое сохранение выбранных артефактов до
остановки. Не превращайте весь scratch в общий том ради логов и не обещайте восстановить
tmpfs через `docker cp` после её размонтирования.

### Ограничение готового Compose

`docker/compose.yaml` содержит полезные образцы разделения sync/push и общего sessions,
но **не является готовым штатным native-профилем stage19r1**: у него `read_only: true`,
а отдельная tmpfs для `/var/lib/gitsync/scratch` не объявлена. Монтирование `/work/tmp`
не решает это; перенаправление туда scratch нарушит требование частного каталога.
Кроме того, произвольный UID требует записи в `/etc/passwd` на старте native, что
конфликтует с read-only root. Не запускайте такой compose без адаптации и повторной
приёмки. Используйте launcher выше; hardened read-only профиль проектируйте отдельно
с частной tmpfs и заранее существующим UID. Команда `docker compose ... config`
проверяет структуру/подстановки, а не работоспособность 1С.

## 9. Регулярный запуск, логи и отправка в Git

Планировщик запускает launcher от одного служебного пользователя, с абсолютным путём
к исходникам/скрипту, приватным окружением, одним каталогом admission и закреплённым
image ID. После reboot проверьте daemon, mounts, доступность лицензии и права до
возобновления расписания. Нельзя считать ожидание flock сохранённой задачей после reboot.

Пример сохранения результата без маскировки exit code через `tee`:

```bash
# /srv/gitsync/logs заранее создан и доступен только оператору.
umask 077
logfile="/srv/gitsync/logs/sync-$(date -u +%Y%m%dT%H%M%SZ)-$$.log"
bash examples/gitsync-run.sh sync-all --config /config/storages.json >"$logfile" 2>&1
rc=$?
printf 'gitsync exit=%s\n' "$rc"
# Планировщику нужно вернуть rc, а не код printf/tee.
```

| Код | Интерпретация |
|---|---|
| 0 | команда завершена; дополнительно проверьте выбранные/отключённые источники и фактический результат |
| 1 | sync или один из источников sync-all завершился ошибкой; возможен частичный прогресс |
| 2 | ошибка CLI/конфигурации или обработанный GitSyncError; не все OS-ошибки сведены к одному коду |
| 64 | ошибка вызова launcher / отсутствующий необходимый инструмент |
| 75 | ожидание внешнего слота истекло, контейнер задания не запускался |
| 77 | небезопасные владелец/права каталога внешней очереди |
| 78 | нарушение scratch-контракта или отказ preflight контейнера |
| 130 | отмена CLI; launcher также возвращает 130 для SIGINT |
| 143 | launcher остановлен SIGTERM |
| иные | код Docker/процесса; исследуйте журнал, OOM и остановки, не переименовывайте всё в license error |

`sync-all` после обычной ошибки продолжает следующие источники и возвращает общий
неуспех. При отмене следующие источники не запускает; уже накопленная ошибка имеет
приоритет над кодом отмены. launcher останавливает свои контейнеры по уникальной метке,
а не по похожему имени; после аварии проверьте, не осталось ли реально живого задания.

Отправка — отдельный разрешённый шаг, **только после проверки результата**:

```bash
git -C /srv/gitsync/repo remote -v
git -C /srv/gitsync/repo status --short
# После проверки адреса назначения, ветки и разрешения на публикацию:
git -C /srv/gitsync/repo push origin HEAD
```

Учётные материалы Git не должны попадать в контейнер синхронизации; пароль хранилища
не нужен отправке. Для SSH проверяйте host key по доверенному каналу, не отключайте
StrictHostKeyChecking. push failure не отменяет локальную синхронизацию: устраняйте
сетевую/правовую проблему и повторяйте отправку, не сбрасывайте VERSION.

## 10. Диагностика

Начинайте с exit code, точного image ID, конфигурации без секретов и периода сбоя.
Разделяйте очередь, preflight, Report, экспорт версии, Git commit и push.

| Симптом | Проверка и действие |
|---|---|
| «Не найдена лицензия» / «не обнаружено свободной лицензии» | сохраните санитизированный `/Out`, стадию и число попыток; сравните jobs=1/2 в контролируемом прогоне; проверьте штатную доступность лицензии с администратором. Причину не объявляйте доказанной по одному сообщению |
| Отказ до версий / Report | это не «новых версий нет» и не обязательно покрывается `retries`; проверьте источник, пользователя, платформу и лицензию |
| GTK / DISPLAY | проверьте native image и штатный Xvfb entrypoint; не пробрасывайте X socket рабочего стола вместо него |
| SIGSEGV/139 до /Out | сверьте комплект платформы, запись UID в `/etc/passwd` и работу native user-entrypoint; read-only root/иной UID требуют отдельной настройки |
| Код 78 / scratch на общем томе | уберите пересекающий mount, верните штатный частный scratch, не выключайте safety env |
| HOME/session dir недоступен | сверьте UID/GID, владельцев и права конкретных каталогов; не запускайте постоянно root и не выдавайте 777 |
| dubious ownership | запускайте владельцем репозитория; `GITSYNC_TRUST_REPO=1` допустим лишь после проверки доверия конкретному `/repo`, не используйте `safe.directory=*` |
| LockBusy / чужой index.lock | найдите активные процессы/задания, дождитесь завершения; не удаляйте замки наугад |
| DirtyWorkingCopy / внешнее изменение | прекратите параллельное редактирование; сохраните diff/копию и разберите изменения, не включайте `--allow-dirty` как универсальный ремонт |
| VERSION больше доступной истории | проверьте, что хранилище не заменено/обрезано и выбран верный subtree; не сбрасывайте маркер автоматически |
| ENOSPC/OOM/137 | проверьте RAM, лимиты контейнера, размер tmpfs и диск Git; уменьшите jobs/queue, обоснованно увеличьте лимиты |
| Таймаут конфигуратора | `designer_timeout` по умолчанию 3600 секунд; изучите реальный размер версии и причины зависания. Это не автоматическая license-retry ошибка |
| Разные даты/SHA при повторной выгрузке | сверьте TZ, AUTHORS, версию платформы, дерево, исходный snapshot и плагины |

Полезные команды оператора (вывод может содержать приватные данные):

```bash
docker ps --no-trunc
docker image inspect --format '{{.Id}}' gitsync-py:native-8.3.27.2130
git -C /srv/gitsync/repo status --porcelain=v1
git -C /srv/gitsync/repo log -10 --format=fuller
git -C /srv/gitsync/repo fsck --full
df -h /srv/gitsync/repo
```

Для активного контейнера по проверенному ID доступны `docker logs <ID>`,
`docker stats --no-stream <ID>`, `docker inspect <ID>` и
`docker exec <ID> df -h /var/lib/gitsync/scratch`. После `--rm` этих данных уже нет:
собирайте host-log заранее. Публикуйте только минимальную санитизированную выдержку.

## 11. Восстановление и rollback

### Обычный сбой / отмена

1. Остановите расписание, убедитесь, что прошлое задание и его конфигураторы завершены.
2. Сохраните приватную копию **всего** Git-каталога с `.git`, рабочим деревом и журналами.
3. Проверьте статус, последние коммиты и VERSION. Код неуспеха не означает, что ни
   одного коммита не было.
4. Устраните причину (права, место, доступность, конфиг), повторите ту же команду с
   тем же образом/источником и `jobs=1`.
5. Проверьте последовательность версий и отсутствие дублирования; только затем
   возобновляйте расписание/отправку.

В `.git` хранится write-ahead journal `gitsync-py-journal.json`, либо отдельный
`gitsync-py-journal-<digest>.json` для subtree. Запись содержит предыдущее/планируемое
состояние файлов и индекса. Подтверждение — опубликованный локальный Git commit,
а не только записанный VERSION. Следующий запуск сверяет журнал до проверки dirty:
неподтверждённую собственную транзакцию откатывает, подтверждённую согласует.
Это не откат коммитов на удалённом сервере.

Если файлы/индекс изменены извне, журнал невалиден или `index.lock` чужой,
восстановление **останавливается с сохранением журнала**. Это защита, а не повод
удалить JSON, VERSION или `.git/index.lock`. Сначала анализ на отдельной копии;
не запускайте `git reset --hard`, `git clean -fdx` или рекурсивную уборку общей папки
как штатный recovery. Не трогайте содержимое scratch соседнего задания.

### Резервные копии

При остановленных writers сохраняйте согласованный snapshot repo целиком (включая
`.git`, журналы и все subtrees), приватных конфигов, журналов приёмки и ID образов.
Секреты архивируются только разрешённым защищённым способом, отдельно от обычного
Git-бэкапа. Backup исходного хранилища/ИБ — отдельная ответственность администратора
1С. Git bundle/remote не включает незакоммиченные файлы и recovery journal и потому
не заменяет полный аварийный snapshot.

Scratch восстанавливать не нужно: выгрузка повторяема из хранилища. Session/admission
lock-файлы — координация, не очередь сохранённых задач. Не удаляйте их при работающих
процессах; при восстановлении на другом узле создайте согласованную общую область
блокировок и исключите одновременную работу старого узла.

### Откат версии инструмента

До обновления зафиксируйте image ID, конфиг и согласованный backup. Сначала прогоните
новый образ на отдельной копии. При отказе остановите writers, сохраните неудачный
snapshot, переключите `GITSYNC_IMAGE` на **ранее сохранённый** ID и испытайте восстановление
на копии. Совместимость recovery journal с более старым кодом не гарантируется;
не отдавайте новый незавершённый journal старой версии вслепую. При необходимости
восстановите целиком предобновлённый snapshot в новый каталог и проверьте его перед
переключением. Простое переключение тега не откатывает изменённые постоянные данные.

### Исправление маркера / истории

`set-version` — операторская смена точки продолжения, **не rollback XML и не удаление
лишних Git-коммитов**. Повышение маркера может пропустить версии, понижение — повторно
импортировать их. Используйте только после backup и доказанного соответствия дерева:

```bash
# Пример синтаксиса; номер обязан выбрать оператор после проверки, не копируйте вслепую.
gitsync-py set-version --workdir /srv/gitsync/repo --version 10 --commit --disable-auto-src
```

Без `--commit` изменяется только файл VERSION, что оставляет незакоммиченное изменение.
Для monorepo `--workdir` указывает на нужный subtree. Переписывание опубликованной
истории/force push здесь не является процедурой восстановления: требуется отдельное
согласование с владельцами репозитория и план для всех потребителей.

## 12. Локальная приёмка перед production

Успешная сборка и help недостаточны. Минимальный протокол:

- [ ] Сохранены source snapshot/commit, image ID/digest core/test/native, версия
  платформы, ОС/архитектура, параметры jobs/queue/retries, TZ и команды без секретов.
- [ ] Тесты запускались из выбранного immutable image; записаны exit code,
  passed/failed/skipped и причины пропусков. Историческое `419 passed, 19 skipped`
  не подставлено вместо нового результата.
- [ ] Fixture smoke подтвердил CLI/Git; отдельно native smoke на копии подтвердил
  Report и экспорт реальной конфигурации, отдельно нужных расширений.
- [ ] jobs=1 прошёл полный требуемый диапазон. VERSION и Git соответствуют отчёту,
  повторный запуск идемпотентен. jobs=2 принят только по собственным повторным прогонам.
- [ ] Два одновременно поданных внешних задания при slots=1 не исполняются одновременно;
  timeout очереди отличается от отказа платформы. Все реальные пути запуска охвачены.
- [ ] Проверены общий sessions, одинаковый UID и одинаковая идентичность источника,
  остановка по сигналу, повтор после прерывания, отсутствие оставшихся writers.
- [ ] Проверены запрет общего scratch, права постоянных каталогов, запас RAM/tmpfs,
  приватность логов и отсутствие секретов/дистрибутивов в Git.
- [ ] Проверено восстановление согласованного backup в отдельный каталог и возврат
  на предыдущий образ. Отдельно проверены права и назначение разрешённой отправки Git.

Не считать доказанными без отдельного теста: все версии/архитектуры 1С, все виды
лицензирования, production TCP-хранилище, Windows/WSL bind-filesystem semantics,
межхостовую блокировку, вредоносный код в своём контейнере, полную работоспособность
конфигурации после выгрузки, бесконечную устойчивость к intermittent failures.

## 13. Что сверено при подготовке документа

Реальные help-вызовы выполнялись из исходников через
`PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src python -m gitsync ...`:
общая справка, `init --help`, `clone --help`, `sync --help`, `sync-all --help`,
`set-version --help`; также `bash examples/gitsync-run.sh --help`.
JSON-пример разобран JSON-парсером, Bash-блоки проверены `bash -n`, относительные ссылки
проверены на существование. В отдельном временном каталоге выполнены fixture
`init → sync → sync`: первый sync зафиксировал версии 1..2, повторный сообщил
«Новых версий нет», все три команды вернули 0. Это не native-приёмка.

Узкий локальный регресс выполнен командой (без записи pytest cache):

```bash
PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src python -m pytest -q -o addopts='' -p no:cacheprovider \
  tests/test_stage19_license_retry.py tests/test_docs_setup_guide.py \
  tests/test_docs_docker_guide.py tests/test_native15_docs.py
```

Результат этого прогона: **52 passed**. Он не заменяет полный suite из immutable image.
Контракты `init`, `clone`, `set-version`, JSON-схема, defaults, retry/recovery и Docker
build targets дополнительно сверены по исходному коду. Docker-сборка/native-доступ
на машине подготовки документа не
подменяются заявлением о ранее выполненной приёмке; команды сборки в этом документе —
инструкция для оператора, а не новые результаты исполнения.
